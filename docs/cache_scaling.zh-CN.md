# KV 前缀复用性能实测

结论：本次 HF stable 配置下，长输入、多问题能明显受益；单题会变慢。缓存减少重复计算，但增加峰值显存。

模型为 Qwen3-VL-4B-Instruct，单张 24 GB NVIDIA GPU。BF16 权重、stable 数值模式（FP32 文本计算）、causal、full projection。固定代码提交 af2215b 和模型 revision，每组预热 2 次、计时 5 次，轮换策略顺序。

输入来自项目自有的同一段 6 秒动画，改变官方视频采样与像素预算：短输入共享前缀 63 tokens，完整输入 100–117 tokens；长输入共享前缀 2,266 tokens，完整输入 2,303–2,320 tokens。这里的短／长表示模型输入规模，不是不同视频时长。

## 如何使用结果

- 单题：本次两个长度下都无需为这一题构建复用缓存。
- 短输入、3 题：差距很小，不据此承诺加速；8／16 题的收益更明显。
- 长输入、3／8／16 题：缓存分别达到普通 batch 的 2.08／3.88／5.19 倍处理速度。
- 长输入、16 题：峰值已分配显存从 15.80 增至 20.60 GiB。KV 会按问题分支复制，并非零复制存储。

## 验证与边界

选入主表的 24 组配置共 120 次正式计时，均成功、无 OOM；所有同输入策略对照的 logits 最大差异为 0，答案一致，候选概率和通过检查。另有 178-token 前缀的中间配置 60 次计时，保存在 results/，不混入主表。

计时包含媒体解码／处理、问题准备、推理、评分，以及缓存方案每次重新构建前缀。模型加载、GC、分配器清理不计时；每次计时前清空 PyTorch allocator，因此这是模型已热身、分配器清空的运行条件，不能直接与此前 README 的热分配器耗时混用。逐题方案在一次 score_many 调用内共享解码，不是 N 次独立 API 请求；普通 batch 保留现有视觉特征去重。

这是一个自有合成视频上的机制与性能实验，不是准确率评测，也不证明原生 BF16、vLLM、Omni-30B 或音频的相同收益。5 次重复不是 5 份独立工作负载，没有据此建立通用开启阈值。

原始记录：[初始实验](validation_evidence/hf-cache-scaling/results/raw.json)、[长输入实验](validation_evidence/hf-cache-scaling/results-long/raw.json)。各目录包含配置、依赖与源代码哈希和加载检查。下方 CPU 核验器重新计算统计并比较原始候选分数，检查的是归档记录，不运行 GPU 推理。

## 执行新的 GPU 测量

先安装 [HF 视频环境](hf.zh-CN.md)，然后使用[英文报告中的完整命令](cache_scaling.md#run-a-new-gpu-measurement)。原始核心提交 `af2215bec742de6d96af4ccb9fb83dd903b4d6c6` 不在公开 Git 历史中；命令会提取当前提交，并将其记录为这次新测量的代码版本。使用仓库自带的动画、固定 revision 的官方权重与独立输出目录，分别运行两个归档脚本：

- `run-initial.py`：短前缀及保留的 178-token 中间配置；
- `run.py`：修正后的 2,266-token 长前缀配置。

两个脚本与实测时字节一致，来源说明字符串保留历史语义；新运行的权重完整性应另行核对。这条流程使用所选代码提交重复测量方法，不能还原缺失的历史源码归档。结果写入新的 `RUN_DIR`，包括逐次分数与耗时、环境、统计和完成标记。仓库冻结记录保持不变；上述 CPU 核验器针对公开的五次重复结果。

请选择空闲 GPU。长输入 16 题缓存配置的峰值已分配／保留显存分别为 20.60／23.11 GiB，尚不包括非 PyTorch 显存开销；容量较小的 GPU 可能 OOM。完成标记只表示所有配置均尝试过，仍需检查每组状态。
